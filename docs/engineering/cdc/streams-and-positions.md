# Change Streams and Positions

How a change stream holds a position, how a read moves it inside the reader's transaction, and how the pieces around it fit. The user-facing guides are [change-streams.md](../../business/data/change-streams.md) and [apply-changes.md](../../business/data/apply-changes.md).

## The feed

`zyron-cdc` records a table's changes in a segmented log under `<data_dir>/cdf/<table_id>/`. Each record carries the change kind, the commit version, the commit instant, the transaction id, an ordinal within the version, the schema epoch the row was written under, and the row image. Sealed segments carry a compressed block and a summary trailer, and a manifest beside them (`manifest.zycdm`) holds the feed's configuration, the segment summaries, a per-version index of record counts, and the span of versions each transaction wrote at. The manifest is a chain of records, one holding the feed whole and one appended per seal with the segment it sealed, the versions it counted and the spans it touched, laid down whole again once the records pass a threshold, so a seal writes what changed rather than the feed's history. The open segment's frames are held in memory beside its file, indexed by the version each one starts at, so a read of the newest changes copies the frames it wants out under the feed's lock and never reopens the file. A writer hands the feed its rows borrowed, and each row is copied once, into the segment buffer. A retention pass that compacts a feed rewrites each sealed segment in place with the records a key's history leaves standing, one segment at a time, and a record removed keeps its place in the numbering a position counts in.

An append is durable through the write-ahead log rather than through a sync of the segment file per commit. Once its bytes are in the open segment's file the feed records them in the log as `ChangeFeedFrames` records naming the feed, the segment, the byte offset and the bytes, ahead of the commit record of the transaction whose changes they frame, so one flush of the log carries both. The segment file itself is synced by the feed's sync passes, by a seal and by a purge. Recovery lays every logged append the manifest's replay point does not cover back into its segment file in log order, cutting the file to the offset each record names, passes over the records of a segment sealed or purged since, and the feed's open then walks the frames as it always has. The manifest records the replay point with every record it writes, the log position of the oldest append no sync pass has reached, and the log keeps its segments from the oldest such point across every open feed.

A segment that reaches its target size is closed by the writer that filled it and sealed by a thread of its own. The writer's part is a summary moved into the sealed list in its raw form and the next file adopted, whose header a sealer prepared ahead of time. The compression and the sealed file's fsync come before the sealer takes the feed's lock, the rename and the summary update happen under it, and the directory sync, the manifest write and the next file's header come after it, so a writer appending meanwhile waits for none of the disk work. Every manifest record is numbered under the lock and written in that order through a gate, so a record written off the lock never lands ahead of the one it follows, and a record given up on unwritten is closed over by the next one, which lays the feed down whole. A stop between a rotation and its sealer leaves the manifest naming a full segment as open with the next one holding frames. Opening the feed walks that chain, seals every raw segment it finds and counts each record once.

A sealed segment stores its records column by column. Each write tells the feed the layout its rows were encoded under, the table's physical columns at the write's epoch or the feed's subset of them, and the feed keeps every layout it has seen in the manifest. When a segment seals, the record headers become one block per field, the rows of each layout become one block per column, and each block is compressed on its own and stored raw when that is smaller. The records keep their written order and each names the layout group its row is in. A read that wants rows rebuilds each one from its group's blocks, byte for byte what was framed, so every reader of frames reads a sliced segment without knowing it. The body ends with a directory naming where every block stands. A scan opens the file, reads the directory off its tail and the header blocks off its front, judges each record from the headers, and fetches only the column blocks its plan takes with positioned reads, so a read of two columns of forty moves a fortieth of the file through memory. A fixed width column read whole and holding no NULL is decompressed straight into the column builder's own storage, and any other column is decoded into a block and gathered from. A layout the feed was never told, or a row that does not walk exactly under its layout, keeps the segment framed, compressed as one block.

A read of a window is a cursor over the segments the window reaches, decided once from their summaries. The cursor holds the segment it stands in and its offset between batches, so a read costs one pass over its files whatever the batch size, and a read continuing from a position skips every segment that ends before it. A lake window is read one commit version at a time.

A window over several files is decoded across the executor's parallel pool. The scan takes the window's files from the cursor as parts, each loading and walking on its own, and hands one to each worker the pool granted, at most that many in flight, awaiting the oldest first. Each worker reads and decompresses its file, judges each record by its transaction's outcome, decodes the rows into column builders and hands back whole batches, so the batches come out in record order and the memory held is bounded by the grant. A worker that meets a change whose transaction has not ended records the file it stood in, the workers on later files stop, and the window closes just before that change the way a read on one thread closes it. A lake window's parts are its commit versions, each derived from the log by the worker that takes it, with the version's rows encoded into one buffer rather than one allocation per change. A window of one file, or a read on a node with no parallel capacity to spare, decodes on the operator's thread through the same row assembly.

The per-version index is what makes a position a count. `records_at_or_below(version)` and `cursor_at_count(count)` turn a version into the number of records recorded at or below it and back. A count names the same change on every member of a group, where the versions differ, so a position replicates as a count and each member turns it back into its own version.

Where a version comes from depends on the node.

- On a node standing alone, the statement records its own changes as it writes them, at the log position of its write.
- On a member of a group, a connection records nothing. The applier records every entry it applies, its own included, at the entry's index and instant, so every member's feed holds the same records at the same versions in the same order.

A write inside a transaction lands in the feed before the transaction decides. The feed keeps the lowest version each unfinished transaction wrote at, pruned by asking the reader's snapshot which transactions have ended, and a read judges each record by its transaction's outcome. A committed record is yielded, an aborted one skipped, and an unfinished one stops the read and closes the window just before it.

## The position lock

A stream's position is a catalog entry, `ChangeStreamEntry`, holding one `(table, version, consumed)` slot per source table. Reading the stream inside a transaction takes the stream's position lock through `StreamPositionLocks` on the transaction manager, keyed by stream id and held by transaction id. The lock is released when the transaction's advances are installed after its commit, or by the transaction's abort, or by the transaction being dropped. The commit path itself never releases it, because the entry has to be in place before the next consumer, waiting on the lock, resolves its windows.

Every stream read resolves its windows after the lock, never at plan time. The consumer that waited on another consumer's commit reads from where that commit left the position, and what stands in the feed at that instant is read under every source feed's lock at once, so a transaction that wrote to two sources is counted in both or open in both. A second read of the same stream inside one transaction reuses the window the first read recorded, so every read of a stream in a transaction yields the same changes whatever has landed since.

The connection's statement path, the generated bodies (`MERGE`, `CALL`, `DO`, a scheduled statement, a materialized view refresh), an `APPLY CHANGES` run and a pipeline stage all install the same change reads and the same change capture on their execution context, and all commit through the same path that logs and installs the advances. A background writer, retention expiry included, writes through the server state's registries with the capture installed, so the rows it removes are the table's changes.

A background writer that produces changes is a writer like any other on a member of a group. The leader runs it, its commit carries a replication changeset, and every member applies the same rows at the same position, so a scheduled statement, a retention expiry, a lake `OPTIMIZE` or clustering rewrite and an outbound delivery each happen once for the group and land on every member. `WriteAuthority` is what a worker asks before it starts such work, true on a node standing alone and on the member that leads, and false on a follower. Work that changes nothing visible, age tiering between a node's own storage tiers, columnar compaction, feature materialization, index vacuum and the lake log's collapse of its own history, runs on every member for itself. A schedule's run is recorded in the same commit as the rows its body wrote, as `OP_SCHEDULE_RUN` carrying the last and next run instants, and a body that fails records its run through the group on its own, so `zyron_sys` reports one `last_run` and one `next_run` for a schedule whichever member answers. A schedule's instants come from the agreed entry's timestamp rather than a member's own clock, which is what makes `CREATE SCHEDULE` and `RESUME SCHEDULE` land the same `next_run` everywhere. While a member runs a binary older than the one that carries schedule runs, due schedules are held and the count held is logged once per change.

The advance is recorded by the scan operator as a `PendingStreamAdvance` on the execution context as soon as the read is under way. The commit path writes the advance into the transaction's own log chain before the commit record and installs the new entry once the commit lands. A rollback discards the record along with everything else the transaction held. On a member of a group the advance travels in the transaction's changeset as `OP_STREAM_ADVANCE`, carrying the consumed counts, gated on every member running a binary that applies it. While a member is older, a transactional consume is refused rather than replicated short, because a position that moved on the leader alone would hand the same changes out again the day another member leads.

## The window

A stream read resolves one window per source table. The upper end is the lowest of every heap source's newest version and the version just below the lowest unfinished transaction across them, so a transaction that touched two sources is wholly inside the read or wholly after it. A lake source's window runs to its own newest version, because a lake version is one commit and its versions are the table's own commit sequence rather than the node's change clock. `WITH (max_rows => n)` asks the heap feeds for one bounded cut across every heap source, the version holding the record at the bound, moved past every transaction that wrote inside the read and again beyond it, until no feed moves it further, and asks each lake source for a cut of its own, the commit holding the record at the bound. The windows are then aligned across every source, heap and lake alike, bounded or not. A transaction with a commit inside one window pulls every other window up to its last commit in that source, and a transaction that cannot be held whole, because one of its commits lies above a source's newest visible version or behind an open transaction there, waits for a later read with every window held below its first commit, until no window moves. The heap feeds answer from the spans they record, and a lake feed's index keeps the transaction each commit is handed over with, the database transaction behind an intent commit as its header records it. The window's `consumed_to` is the record count at its upper end, which is what the advance carries.

A stream over a view reads the view's one base table through the view's projection and predicate. A stream over several tables yields the union of their columns by name, an absent column reading NULL, and `_source_table`.

## Lake tables

A lake table has no change file. Its transaction log is the change record, and `zyron-wire`'s change feed bridge derives change records from the log's versions between two commits. A compaction produces no change records, a deletion vector delete produces deletes, and a truncate produces one truncate record.

On a member of a group the log's versions and the data files they name both arrive through the replication log. A lake commit's changeset carries every data and index file the version adds as `OP_LAKE_FILE` pieces, each no larger than a changeset chunk, streamed ahead of the catalog op that names the version, so a follower holds the bytes before it holds the version. The applier accumulates the pieces under the node's temporary directory, moves a file whole into the lake's data directory once its last piece lands, and holds the version's partition staged until the entry commits, so a version is never visible with a file missing and an abandoned entry leaves nothing behind. The count of records each commit yields is then derived from the same files on every member, and a position over a lake table names the same record everywhere. A lake write is refused with `UpgradeRefused` while a member runs a binary older than the one that carries lake files, because a version whose files reached the leader alone would be a version a follower cannot read. A commit on the head a branch keeps on a table travels as `OP_LAKE_BRANCH_VERSION`, naming the branch and the version it forked the table at, so a member that has not forked the table forks it at that version and applies the commit on the same head, and a member whose head forked elsewhere refuses it rather than building on it.

A stream position over a lake table is the same pair a heap table's is, a commit version and the count of records at or below it, counted from the version the feed was turned on at. A heap feed counts its records as it writes them. A lake feed writes nothing, so the count of what each commit yields is taken from the log the first time the commit is asked about and kept in the feed's record index, `cdf/<table id>/lake_index.zycdi`, one entry per commit that yields records with the running count before it. The index is durable because retention reclaims the log's oldest versions and the counts of a reclaimed version have to outlive it, so a position that counts from the feed's first version still names the same record after the versions beneath it are gone. The index also keeps the before image setting in force for every commit it counted, and a read of a commit derives its records under that same setting, so a change of the setting takes effect above the commits already counted and never moves a record a position names. `MAX ROWS` on a lake stream bounds records, the cut landing on the commit holding the record at the bound and moving with the other sources' windows. A transaction whose commits publish one table at a time is handed over by no source until every commit is visible, since a commit above the head readers see holds the transaction open on every other source. A stream on a lake table is stale exactly when time travel to its position fails, because the position names a version the log no longer holds. A stream on a branch over a lake table reads the head the branch keeps on the table, counted into an index of the branch's own under the table's feed directory and beginning at the version the branch forked the table at, and a branch that has not forked the table forks it at the table's current version on the stream's first use, the way a branch's feed on a heap table opens.

## Schema epochs

Every change record carries the schema epoch the row was written under. A read decodes each record through that epoch and projects to the table's current columns by default, so a column added after a change reads NULL in it and a dropped column is absent. `schema => 'as_of_change'` renders each record through the columns it was written under, dropped columns included. A widened type casts forward. A stream naming a dropped column needs attention rather than being stale, keeps its position, and resumes once its column list is corrected. A narrowing type change on a table with streams is refused unless acknowledged, and the acknowledgement marks every stream over the table as needing attention.

A feed configured with `cdf_columns` records each row narrowed to the named columns plus the table's key, and flags the record. The write hook walks the row once through the epoch's layout, copying the kept columns' bytes and stepping over the rest by width, so nothing is decoded and the record is the row a table of only those columns would have encoded. The table's catalog entry keeps one column list per schema epoch at which the list changed, and every change of the list mints a schema epoch, so the epoch a record carries names both the table's layout and the list in force. A flagged record decodes through the epoch's layout narrowed to that list. A column the list left out is not absent the way a column added later is, because the table had a value the feed never recorded, so a read asking for it fails naming the column and the epoch on the first such record rather than answering NULL. A primary key declared after the list joins the recorded set under an epoch of its own.

A feed keeps rows the heap has rewritten or deleted, each decoding through the layout it was written under, so vacuum's retirement of spent epochs takes the lowest epoch any feed of the table still holds, its branches' feeds included, as a floor. Each segment summary records the lowest epoch among its records, and the floor is the minimum over the segments the feed still holds, so a layout retires once the last record written under it is purged.

## Branches

A branch's changes are recorded in a feed of their own, beneath the table's feed directory, opened when the branch is created at the table's current version. That version is the branch point. A stream created on a branch reads the branch's feed and keeps a position of its own. A `table_changes` read inside a branch is split at the branch point, the table's feed below it and the branch's above it. Merging a branch lands its rows on the table through the ordinary write path, so the table's feed records them, and consumes the branch's streams and feeds with the branch. Dropping a branch does the same without the merge.

## Outbound delivery

An outbound CDC stream consumes a change stream. The pump on the node standing alone or leading its group reads the stream under its position lock, delivers to the sink, and moves the position in a commit of its own once the sink has taken the records. There is no second checkpoint. A stream state file written before positions were change streams named a replication slot, and the state migrator names the change stream in its place, which the pump creates on the first pass that finds none, at the place the slot had reached, before retiring the slot.

## What the web app shows

The web app builds against what this phase exposes, and nothing here is shaped for it in particular. A change stream is its own catalog object kind, listed apart from the streaming job kind, and every column the web app renders for one comes from `zyron_sys.cdc.change_streams`, so the position, the pending rows, the lag, the mode and whether the stream is stale or needs attention are the view's columns and the reset, drop and peek actions are `ALTER CHANGE STREAM ... RESET`, `DROP CHANGE STREAM` and a read `WITH (peek => true)`. A table whose feed is on carries a changes tab, which is `table_changes` over the version range picked, filtered on `_change_type`, showing the metadata columns beside the rows, and a stream created from where the picker stands is `CREATE CHANGE STREAM ... AT VERSION`. The jobs designer offers the `CONSUME CHANGES` and `APPLY CHANGES` stages and the `ON CHANGE DATA` trigger, reading lag for its stream picker from the same view. A lineage edge of kind changes runs from a source table through a stream to the target an `APPLY CHANGES` maintains, which `zyron_sys.cdc.apply_runs` records target by source.

## What a change stream is not

A change stream is not a queue. A queue hands a message to one consumer and forgets it, and a message is gone once acknowledged. A change stream is a position over a record that stays for its retention, so a second stream over the same table reads the same changes from wherever it stands, and a reset moves a stream back over changes it already consumed.

A change stream is not a streaming job either. A streaming job runs a query continuously over a source and writes a sink on its own schedule. A change stream is read by whatever transaction reads it, at that transaction's pace, and moves only when that transaction commits.
